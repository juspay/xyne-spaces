# Tags Module Developer Guide

The tags module has two separate responsibilities:

- Manual tag management through HTTP APIs.
- Asynchronous tag generation through the worker pipeline.

API requests should not wait for generated tags. If a caller starts generation, return an accepted response with the job id or a status message, then let the caller read tags later with `GET /api/tags`.

## Files

- `routes.ts`: Express routes under `/api/tags`.
- `controller.ts`: HTTP request handling only.
- `service.ts`: tag and tag config business logic.
- `pipeline.ts`: async tag generation queue and worker processing.
- `schema.ts`: shared Zod schemas for API bodies, configs, generated tags, and pipeline payloads.
- `types.ts`: TypeScript types inferred from shared schemas.
- `generators/llm`: LLM tag generator and its output schema.
- `generators/automated`: automated script generator, output schema, and config validation.

## HTTP API

All routes are mounted under `/api/tags` and require auth.

Manual tag operations:

```txt
GET    /api/tags
POST   /api/tags
PUT    /api/tags
PATCH  /api/tags
DELETE /api/tags
```

Config operations:

```txt
GET    /api/tags/configs?sourceType=<sourceType>
GET    /api/tags/configs/:configKey
POST   /api/tags/configs
PATCH  /api/tags/configs/:configKey
DELETE /api/tags/configs/:configKey
```

`GET /api/tags/configs?sourceType=<sourceType>` lists all active configs for that `sourceType` in the caller's workspace — useful for discovering existing configs (e.g. per-channel configs) before creating a new one.

`PUT /api/tags` is for replacing manual tags for one category. It is not the async generation endpoint.

## Workspaces

`Tag` and `TagsConfig` rows are stamped with `workspaceId` for per-workspace filtering and ACL. `workspaceId` is always derived server-side from the authenticated user (`req.user.workspaceId`) — it is never accepted from the request body or query string. Internal callers (e.g. the generation pipeline) pass the producer record's `workspaceId` explicitly (e.g. `Ticket.workspaceId`).

Example manual override:

```json
{
  "sourceId": "ticket-123",
  "sourceType": "ticket",
  "tagCategory": "priority",
  "tags": ["high"]
}
```

For `POST`, `PUT`, `PATCH`, and `DELETE /api/tags`, the target `tagCategory` must be configured with `method: "manual"`.

If the category is configured as `llm` or `automated`, the caller must explicitly pass:

```json
{
  "override": true
}
```

This keeps accidental manual edits from changing generated categories while still allowing intentional administrative overrides.

If an active config exists and the category is missing from it, add the category to the config first. `override` is only for intentionally editing configured non-manual categories.

The manual/override check is resolved against a specific config by passing `configKey` on the request body. A `sourceType` can have multiple active configs (e.g. one per Desk channel), so `configKey` identifies which one governs this tag. If `configKey` is omitted, the check is skipped (no restriction), matching the "no active config found" behavior.

## Config Shape

Configs are versioned by soft-deleting the old active row and inserting a new row. The active config is read by `configKey`.

Example:

```json
{
  "configKey": "ticket-tags",
  "sourceType": "ticket",
  "config": {
    "categories": {
      "priority": {
        "method": "llm",
        "tags": ["low", "medium", "high"],
        "count": 1,
        "is_new_tag_allowed": false,
        "prompt": "Classify the ticket priority."
      },
      "product-area": {
        "method": "llm",
        "tags": ["billing", "integrations", "security"],
        "is_new_tag_allowed": true,
        "blacklist": ["unknown"]
      },
      "priority": {
        "method": "automated",
        "script": "(context) => String(context).toLowerCase().includes('urgent') ? [{ category: 'priority', tag: 'high', reason: 'urgent keyword matched' }] : []",
        "tags": ["low", "medium", "high"],
        "count": 1,
        "is_new_tag_allowed": false
      },
      "owner": {
        "method": "manual",
        "tags": []
      }
    }
  }
}
```

Category methods:

- `manual`: managed only through manual APIs. The pipeline skips these categories.
- `llm`: generated by the LLM generator.
- `automated`: generated by the script generator.

LLM behavior:

- `tags` is the allowed vocabulary.
- `count` is optional and is passed as guidance to the model.
- `prompt` adds category-specific instructions.
- `blacklist` rejects generated tags for that category.
- `is_new_tag_allowed` allows the LLM to introduce a tag outside `tags`.

If `is_new_tag_allowed` is true and the LLM returns a new tag, the pipeline folds that tag back into the active config before persisting tags.

Automated behavior:

- `script` is required for every automated category.
- The script is a JavaScript function expression: `(context, config) => tags[]`.
- `context` is the source text returned by the registered context builder.
- `config` is that category's config object.
- The script must return an array of `{ category, tag, reason? }`.
- `tags` is the allowed vocabulary.
- `blacklist` rejects generated tags for that category.
- `count` caps generated tags only when explicitly configured.
- `is_new_tag_allowed` allows the script to introduce a tag outside `tags`.
- `script_timeout_ms` can be configured per category up to 5 minutes, matching the queue lock duration.
- Config create/update dry-runs scripts with `sampleContext` when provided, otherwise with a default sample context.

Example automated script:

```json
{
  "method": "automated",
  "script": "(context) => String(context).toLowerCase().includes('urgent') ? [{ category: 'priority', tag: 'high', reason: 'urgent keyword matched' }] : []",
  "tags": ["low", "medium", "high"],
  "is_new_tag_allowed": false
}
```

## Pipeline Usage

The pipeline is controlled by:

```txt
ENABLE_TAG_GENERATION_PIPELINE=true
```

When disabled:

- `initialize()` logs and returns.
- `addGenerationJob()` throws.
- worker startup skips initialization.

Register a context builder for each supported `sourceType` before enqueueing generation:

```ts
import { tagGenerationPipeline } from '@/tags';

tagGenerationPipeline.registerContextBuilder('ticket', async (sourceId, sourceType) => {
  // Fetch and render the text that the generators should classify.
  return `Source ${sourceType}/${sourceId} context...`;
});
```

Start the pipeline from worker startup:

```ts
await tagGenerationPipeline.initialize();
```

Enqueue generation:

```ts
const jobId = await tagGenerationPipeline.addGenerationJob({
  sourceId: 'ticket-123',
  sourceType: 'ticket',
  workspaceId: ticket.workspaceId,
  configKey: 'ticket-tags',
});
```

Return an async response if this is triggered from an API:

```ts
return res.status(202).json({
  success: true,
  jobId,
  message: 'Tag generation queued. Read tags later from GET /api/tags.',
});
```

Do not wait for generated tags in the API request. The queue can be processed by a different worker process, so request handlers should not depend on in-memory completion events.

## Completion And Failure Events

The pipeline exposes source-type events for process-local consumers:

```ts
tagGenerationPipeline.onCompleted('ticket', (result) => {
  // result.jobId, result.sourceId, result.sourceType, result.tags
});

tagGenerationPipeline.onFailed('ticket', (error) => {
  // error.jobId, error.sourceId, error.sourceType, error.error
});
```

These events are useful inside the worker process. They are not a cross-process API contract.

For external callers, use persisted tags and queue status instead of in-memory events.

## Queue Settings

The Bull queue name is `tag-generation`, with job name `generate-tags`.

Current settings:

- `attempts: 3`
- exponential backoff starting at 2 seconds
- `removeOnComplete: true`
- keep the last 100 failed jobs
- `lockDuration: 5 minutes`
- `stalledInterval: 1 minute`
- `maxStalledCount: 1`

The 5 minute lock gives slower LLM calls time to complete without being marked stalled too early.

## Data Flow

1. A source integration registers a context builder for its `sourceType`.
2. Caller enqueues a generation job with `sourceId`, `sourceType`, `workspaceId`, and `configKey`.
3. Worker loads the active config for `configKey`.
4. Worker builds source context using the registered context builder.
5. Worker groups categories by method.
6. Worker skips manual categories.
7. Worker runs registered generators for non-manual categories.
8. Worker optionally updates config with newly allowed LLM tags.
9. Worker replaces persisted tags for generated categories.
10. Manual tags remain untouched by generated categories.

## Important Rules

- Keep API routes for manual edits and config CRUD.
- Keep generation async.
- Do not add an API that waits for the pipeline result.
- Do not register generators outside `TagGenerationPipeline`; generator registration is internal.
- Add reusable request/config/output shapes in `schema.ts`.
- Infer TypeScript types from schemas in `types.ts`.
