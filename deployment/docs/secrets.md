## Principles

- Nothing is generated by Terraform or inside the cluster. `scripts/secrets.sh --env <env>`
  generates every required value on your workstation into `01-infra.secrets.tfvars` and
  `02-platform.secrets.tfvars` (mode 600, never printed), and `setup.sh` passes each after its
  stack's tfvars. Keep secrets only there, so the plain tfvars can be reviewed and versioned
  while the secrets files are not. You can also write those files, or the values into the plain
  tfvars, yourself as below; the doctor fails when a variable is set in both.
- `02-platform` validates every value and writes it into Kubernetes Secrets as is.
- The only derived values are connection URLs: `modules/platform` assembles
  `postgresql://<user>:<password>@<host>:<port>/<db>?sslmode=<mode>` and
  `redis://:<auth>@<host>:<port>` (or `rediss://` when TLS) from the contract.
- The Helm charts never create Secrets; they reference the names below.
- Secret values are Terraform `sensitive` variables: they do not appear in plan output, but they
  are stored in the Terraform state. The state bucket is therefore as sensitive as the values.

## Every secret, where it comes from, where it goes

### `01-infra.tfvars`

| Variable | Constraint | Ends up in |
|---|---|---|
| `postgres_password` | >= 16 characters (`02-platform` check); RDS also forbids `/ @ "` and spaces | password of the managed role; `DATABASE_URL`, `COMMON_DATABASE_URL`, `DATABASE_READ_REPLICA_POOL_URL`, `ZERO_UPSTREAM_DB` in `xyne-backend-secrets`; the three `ZERO_*_DB` in `xyne-zero-secrets`; `DATABASE_URL` in `xyne-claw-auth-secrets`; `password` in `xyne-pg-app` (`incluster`) |
| `redis_auth` | AWS `managed`: required, 16–128 printable characters excluding `/ @ "`; `incluster`: required; GCP/Azure `managed`: ignored (the service's own AUTH string / access key is used) | `REDIS_URL` and `REDIS_PASSWORD` in `xyne-backend-secrets`; `REDIS_PASSWORD` in `xyne-claw-secrets` and `xyne-claw-auth-secrets`; `password` in `xyne-redis-auth` (`incluster`); the LiveKit server config |
| `storage_credentials.access_key_id`, `.secret_access_key` | required for `incluster` and `external`; must be empty for `managed` (workload identity) | `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` in `xyne-backend-secrets` and `xyne-ysweet-secrets`; `rootUser` / `rootPassword` in `xyne-minio-root` (`incluster`) |
| `livekit_api_key`, `livekit_api_secret` | both required when `livekit_enabled` | the LiveKit server and egress config in the cloud secret store; `LIVEKIT_API_KEY` / `LIVEKIT_API_SECRET` in `xyne-transcription-agent-secrets` |
| `livekit_turn_cert_secret` | a name in the cloud secret store, not the value | fetched by the LiveKit VMs at boot |

### `02-platform.tfvars` — `app_secrets`

| Field | Constraint | Protects | Ends up in |
|---|---|---|---|
| `jwt_secret` | >= 32 | session tokens | `JWT_SECRET` in `xyne-backend-secrets` |
| `zero_auth_secret` | >= 32 | Zero client tokens; backend and Zero must share it | `ZERO_AUTH_SECRET` in `xyne-backend-secrets` and `xyne-zero-secrets` |
| `zero_admin_password` | >= 16 | Zero's admin endpoints | `ZERO_ADMIN_PASSWORD` in `xyne-zero-secrets` |
| `encryption_key` | exactly 64 hex characters (32 bytes) | data at rest encrypted by the backend | `ENCRYPTION_KEY` in `xyne-backend-secrets` |
| `internal_s2s_key` | >= 32 | service-to-service calls | `INTERNAL_S2S_KEY` in `xyne-backend-secrets`, `xyne-claw-secrets`, `xyne-claw-auth-secrets` |
| `claw_s2s_key` | >= 32 | claw ↔ claw-auth | `XYNE_CLAW_S2S_KEY` in `xyne-claw-secrets` and `xyne-claw-auth-secrets` |
| `claw_auth_encryption_key` | exactly 64 hex characters | credentials stored by claw-auth | `ENCRYPTION_KEY` in `xyne-claw-auth-secrets` |
| `ysweet_auth` | non-empty; the `private_key` from `y-sweet gen-auth --json` | the y-sweet server's signing key | `Y_SWEET_AUTH` in `xyne-ysweet-secrets` |
| `ysweet_server_token` | non-empty; the `server_token` from the same run | the token the backend presents to y-sweet | `Y_SWEET_SERVER_TOKEN` in `xyne-backend-secrets` |
| `transcription_agent_api_key` | >= 32 | backend ↔ transcription agent | `TRANSCRIPTION_AGENT_API_KEY` in `xyne-transcription-agent-secrets` |
| `litellm_api_key` | optional | model access for claw | `LITELLM_API_KEY` in `xyne-claw-secrets` |
| `hindsight_api_key` | optional | claw's key for the Hindsight memory API; leave empty when the deployed addon needs no auth | `HINDSIGHT_API_KEY` in `xyne-claw-secrets` |
| `hindsight_llm_api_key` | optional | Hindsight's own LLM provider key, only for `enable_hindsight = true`; without it Hindsight starts but extracts no facts | `HINDSIGHT_API_LLM_API_KEY` in `hindsight-secrets`, namespace `hindsight`, read through the chart's `existingSecret` |
| `google_client_id`, `google_client_secret` | **required**: the backend does not start without them; see [Google sign-in](#google-sign-in) | the Google OAuth client the backend and claw-auth sign in with | `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` in `xyne-backend-secrets` and `xyne-claw-auth-secrets` |

`ysweet_auth` and `ysweet_server_token` must come from the **same** `gen-auth` run; the token is
derived from the key.

| Secret | Type | Keys | Created when |
|---|---|---|---|
| `xyne-backend-secrets` | Opaque | `DATABASE_URL`, `COMMON_DATABASE_URL`, `DATABASE_READ_REPLICA_POOL_URL`, `ZERO_UPSTREAM_DB`, `REDIS_URL`, `REDIS_PASSWORD`, `JWT_SECRET`, `ZERO_AUTH_SECRET`, `ENCRYPTION_KEY`, `INTERNAL_S2S_KEY`, `Y_SWEET_SERVER_TOKEN`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` | always |
| `xyne-zero-secrets` | Opaque | `ZERO_UPSTREAM_DB`, `ZERO_CVR_DB`, `ZERO_CHANGE_DB`, `ZERO_AUTH_SECRET`, `ZERO_ADMIN_PASSWORD` | always |
| `xyne-claw-secrets` | Opaque | `XYNE_CLAW_S2S_KEY`, `INTERNAL_S2S_KEY`, `LITELLM_API_KEY`, `REDIS_PASSWORD` | always |
| `xyne-claw-auth-secrets` | Opaque | `DATABASE_URL`, `ENCRYPTION_KEY`, `XYNE_CLAW_S2S_KEY`, `INTERNAL_S2S_KEY`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `REDIS_PASSWORD` | always |
| `xyne-ysweet-secrets` | Opaque | `Y_SWEET_AUTH`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` | always |
| `xyne-transcription-agent-secrets` | Opaque | `LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET`, `TRANSCRIPTION_AGENT_API_KEY` | always |
| `xyne-pg-app` | `kubernetes.io/basic-auth` | `username`, `password` | `postgres_mode = "incluster"` |
| `xyne-redis-auth` | Opaque | `password` | `redis_mode = "incluster"` |
| `xyne-minio-root` | Opaque | `rootUser`, `rootPassword` | `storage_mode = "incluster"` |

`terraform -chdir=deployment/terraform/stacks/<cloud>/02-platform output secret_names` lists
the ones created for an environment.

## Generating the values

```bash
# >= 16 characters, URL- and RDS-safe alphabet
openssl rand -base64 24 | tr -d '/+=' | cut -c1-24
# >= 32 characters
openssl rand -base64 48 | tr -d '/+=' | cut -c1-48
# exactly 64 hex characters (32 bytes)
openssl rand -hex 32
# y-sweet key pair (the image has no entrypoint; name the binary)
docker run --rm ghcr.io/juspay/y-sweet:sha-221d5af y-sweet gen-auth --json
# {
#   "private_key": "…",     -> ysweet_auth
#   "server_token": "…"     -> ysweet_server_token
# }
# LiveKit key pair
docker run --rm livekit/livekit-server:v1.9.1 generate-keys
# API Key:  API…            -> livekit_api_key
# API Secret: …             -> livekit_api_secret
```

The y-sweet tag is the `appVersion` of `helm-charts/charts/xyne-ysweet/Chart.yaml`; the LiveKit
tag is the default of `livekit_server_image`. Use whatever your `chart_revision` pins.

A complete set in one go, printed as HCL you can paste:

```bash
r() { openssl rand -base64 48 | tr -d '/+=' | cut -c1-"$1"; }
YS="$(docker run --rm ghcr.io/juspay/y-sweet:sha-221d5af y-sweet gen-auth --json)"
cat <<EOF
postgres_password = "$(r 24)"

app_secrets = {
  jwt_secret                  = "$(r 48)"
  zero_auth_secret            = "$(r 48)"
  zero_admin_password         = "$(r 24)"
  encryption_key              = "$(openssl rand -hex 32)"
  internal_s2s_key            = "$(r 48)"
  claw_s2s_key                = "$(r 48)"
  claw_auth_encryption_key    = "$(openssl rand -hex 32)"
  ysweet_auth                 = "$(printf '%s' "$YS" | jq -r .private_key)"
  ysweet_server_token         = "$(printf '%s' "$YS" | jq -r .server_token)"
  transcription_agent_api_key = "$(r 48)"
}
EOF
```

## Google sign-in

Users sign in with Google, so every install needs a Google OAuth client. The backend refuses to
start without `google_client_id` and `google_client_secret`, and the doctor fails until both are
set. The client can live in any Google Cloud project; it does not have to be on the cloud you
install on.

1. **Consent screen.** In <https://console.cloud.google.com/apis/credentials/consent>, configure
   the OAuth consent screen: *Internal* when every user is in your Google Workspace, otherwise
   *External*, adding your domain under authorised domains.
2. **Client.** In <https://console.cloud.google.com/apis/credentials>, choose *Create
   credentials → OAuth client ID → Web application* and set, with `domain` from
   `02-platform.tfvars`:

   | Field | Value |
   |---|---|
   | Authorized JavaScript origins | `https://<domain>` |
   | Authorized redirect URIs | `https://<domain>/api/auth/exchange` |

3. **Hand it to the install.** `secrets.sh` asks for the client ID and secret when it writes
   `02-platform.secrets.tfvars`, after printing these steps with your domain filled in. It also
   reads `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` from the environment, for runs without a
   terminal. Given neither, it writes placeholders and the doctor stops you before `setup.sh`.

The client ID ends in `.apps.googleusercontent.com`. To change the client on a running install,
edit the two values in `02-platform.secrets.tfvars`, run `setup.sh --only platform`, and restart
the backend and claw-auth ([Rotation](#rotation)).

## LiveKit keys and the TURN certificate bundle

`livekit_api_key` / `livekit_api_secret` are rendered into the server configuration (`keys:`)
and the egress configuration, stored in the cloud's secret store by `01-infra`, and copied into
`xyne-transcription-agent-secrets` by `02-platform`. The backend and the agent sign room tokens
with them.

TURN over TLS is optional. The bundle is a single PEM file: the full certificate chain for
`turn.<domain>` followed by its private key. The VM's cloud-init splits it into
`/etc/livekit/turn/cert.pem` and `key.pem`.

| Cloud | Store the bundle | Variable |
|---|---|---|
| GCP | `gcloud secrets create xyne-livekit-turn-cert --data-file=turn-bundle.pem --replication-policy=automatic` | `livekit_turn_cert_secret = "xyne-livekit-turn-cert"` (secret id in the same project) |
| AWS | `aws secretsmanager create-secret --name xyne/livekit/turn-cert --secret-string file://turn-bundle.pem` | `livekit_turn_cert_secret = "xyne/livekit/turn-cert"` |
| Azure | `az keyvault secret set --vault-name <livekit vault> --name livekit-turn-cert --file turn-bundle.pem` | `livekit_turn_cert_secret = "livekit-turn-cert"` (a secret **name** in the LiveKit Key Vault) |

The signalling certificate for `livekit.<domain>` is separate: managed by GCP, ACM on AWS
(`livekit_certificate_arn` or automatic with `dns_zone`), a Key Vault certificate on Azure
(`livekit_certificate_secret_id`). See each cloud guide's TLS section.

## Adding secrets the tree does not know about

`extra_secret_data` merges keys into any of the nine Secrets:

```hcl
extra_secret_data = {
  xyne-backend-secrets = {
    GOOGLE_REFRESH_TOKEN = "…"
    EMAIL_FROM           = "no-reply@example.com"
  }
  xyne-claw-secrets = {
    LITELLM_URL = "https://llm-gateway.internal.example.com"
  }
}
```

A key is only used by a pod if the chart maps it; add `secretEnv` entries through
`apps.<chart>.values` (single keys) or `envFromSecrets: [xyne-backend-secrets]` (the whole
Secret; note that this also injects the empty `AWS_ACCESS_KEY_ID` in `managed` storage mode,
which the AWS SDK treats as set). Secrets outside these nine (registry pull secrets, backup
credentials such as `xyne-pg-backup`) are created by you with `kubectl` or by an overlay.

## Rotation

Every rotation is: change the value in the `.tfvars`, re-apply the stack that owns it, restart
the pods that read it. Terraform replaces the Secret data in place; pods pick up a Secret change
only on restart.

| Value | Re-apply | Then |
|---|---|---|
| any `app_secrets` field, `extra_secret_data` | `setup.sh --env prod --only platform` | `kubectl -n xyne rollout restart deployment/xyne-backend deployment/xyne-worker-default …` for the readers: backend + workers (`jwt_secret`, `internal_s2s_key`, `encryption_key`), backend + zero + zero-replication (`zero_auth_secret`), ysweet + backend (`ysweet_*`), claw + claw-auth (`claw_s2s_key`, `litellm_api_key`), backend + claw-auth (`google_client_id`, `google_client_secret`), transcription-agent (`transcription_agent_api_key`) |
| `postgres_password` (`managed`) | `setup.sh --env prod` (both: `01-infra` changes the role's password, `02-platform` rewrites the URLs) | restart backend, workers, zero, zero-replication, claw-auth |
| `postgres_password` (`incluster`) | `--only platform` rewrites `xyne-pg-app`; CNPG applies the new password to the role | restart the same set |
| `redis_auth` (AWS `managed`) | `setup.sh --env prod` (ElastiCache rotates with `ROTATE` strategy, old and new tokens both valid until the next change) | restart backend, workers, claw, claw-auth; LiveKit instances need a rolling replacement of the group |
| `redis_auth` (`incluster`) | `setup.sh --env prod` (`01-infra` passes it through the contract; `02-platform` rewrites `xyne-redis-auth`) | `kubectl -n xyne rollout restart statefulset/xyne-redis`, then the apps |
| `storage_credentials` (`incluster`/`external`) | `setup.sh --env prod` | restart minio (`incluster`), backend, workers, ysweet, dashboard-edge, transcription-agent |
| `livekit_api_key` / `livekit_api_secret` | `setup.sh --env prod` (`01-infra` rewrites the config secrets, `02-platform` the agent Secret) | replace the LiveKit instances so they reload the config (see [operations.md](operations.md#scaling)), restart backend and transcription-agent |

Rotating a value that other systems hold (`ysweet_server_token` is only known to the backend
and y-sweet; `zero_auth_secret` invalidates every client session) has application-level
consequences beyond the restart; plan a maintenance window for `jwt_secret`, `zero_auth_secret`
and `encryption_key` (data encrypted with the old key is unreadable after the change).

`encryption_key` and `claw_auth_encryption_key` cannot be rotated without re-encrypting stored
data; the application provides no re-encryption tooling in this tree.

## What never to commit

- `deployment/environments/<env>/` for any `<env>` that is not `example-*`: ignored by
  `deployment/environments/.gitignore` (`*/` with `!example-*/`). Keep real environments in a
  private repository and use `--env-dir`.
- `deployment/terraform/stacks/*/*/backend.tf`, generated by `setup.sh`: ignored by
  `deployment/terraform/.gitignore` (`**/backend.tf`), along with `**/.terraform/`,
  `*.tfstate*` and `*.tfplan`.
- The Terraform state itself holds every sensitive value: restrict the state bucket to the
  deployers, keep versioning on (the scripts enable it), and never copy a state file into a
  repository.
- The example values in `example-*/` are placeholders and are rejected by `doctor.sh`; do not
  "fix" the doctor by removing the check.
