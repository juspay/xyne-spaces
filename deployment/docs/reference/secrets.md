## Principles

- Nothing is generated by Terraform or in the cluster. Every value is an input you supply, so
  every value is yours to rotate and audit.
- Secrets live in `01-infra.secrets.tfvars` and `02-platform.secrets.tfvars` in the environment
  directory, readable only by you. The plain tfvars hold no secrets, so they can be reviewed and
  versioned. The doctor fails when a variable is set in both.
- `02-platform` validates each value and writes it into Kubernetes Secrets as is. The only derived
  values are the connection URLs it assembles from the contract.
- The charts never create Secrets; they reference the names below.
- Sensitive variables stay out of plan output but are stored in the Terraform state, so the state
  bucket is as sensitive as the values.

## Generating them

```bash
deployment/scripts/secrets.sh --env prod
```

It writes every required value and prints none. It asks for the Google client
([below](#google-sign-in)), or reads `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` from the
environment. An existing `01-infra.secrets.tfvars` only gets what it lacks appended (the LiveKit
keys when you turn LiveKit on, for example); an existing `02-platform.secrets.tfvars` is left
alone. `--force` rewrites both files, which rotates everything in them. `--dry-run` lists what
would be written, masked.

By hand, the constraints are:

```bash
openssl rand -base64 24 | tr -d '/+=' | cut -c1-24     # 16+ characters, RDS-safe (postgres_password, redis_auth, zero_admin_password)
openssl rand -base64 48 | tr -d '/+=' | cut -c1-48     # 32+ characters (jwt_secret, zero_auth_secret, internal_s2s_key, claw_s2s_key, transcription_agent_api_key)
openssl rand -hex 32                                   # exactly 64 hex characters (encryption_key, claw_auth_encryption_key)
docker run --rm ghcr.io/juspay/y-sweet:<tag> y-sweet gen-auth --json      # private_key -> ysweet_auth, server_token -> ysweet_server_token
docker run --rm livekit/livekit-server:v1.9.1 generate-keys              # livekit_api_key, livekit_api_secret
```

The y-sweet tag is the `appVersion` of `helm-charts/charts/xyne-ysweet/Chart.yaml`.

## `01-infra` secrets

| Variable | Constraint | Ends up in |
|---|---|---|
| `postgres_password` | 16+ characters; RDS also refuses `/ @ "` and spaces | the database role; every database URL in `xyne-backend-secrets`, `xyne-zero-secrets`, `xyne-claw-auth-secrets`; `xyne-pg-app` in `incluster` mode |
| `redis_auth` | AWS `managed`: required, 16 to 128 characters without `/ @ "`; `incluster`: required; GCP and Azure `managed`: not used (the service's own AUTH is read) | `REDIS_URL` and `REDIS_PASSWORD` for the apps; `xyne-redis-auth` in `incluster` mode; the LiveKit server config |
| `storage_credentials` | required for `incluster` and `external` storage; empty for `managed` | S3 keys in `xyne-backend-secrets` and `xyne-ysweet-secrets`; `xyne-minio-root` in `incluster` mode |
| `livekit_api_key`, `livekit_api_secret` | required with `livekit_enabled` | the LiveKit server and egress config in the cloud's secret store; `xyne-backend-secrets` and `xyne-transcription-agent-secrets` |
| `livekit_turn_cert_secret` | the *name* of a secret in the cloud's store, not a value | fetched by the LiveKit VMs at boot |

## `02-platform` secrets: `app_secrets`

| Field | Constraint | Protects | Ends up in |
|---|---|---|---|
| `jwt_secret` | 32+ | session tokens | `xyne-backend-secrets` |
| `zero_auth_secret` | 32+ | Zero client tokens; the backend and Zero share it | `xyne-backend-secrets`, `xyne-zero-secrets` |
| `zero_admin_password` | 16+ | Zero's admin endpoints | `xyne-zero-secrets` |
| `encryption_key` | exactly 64 hex | data the backend encrypts at rest | `xyne-backend-secrets` |
| `internal_s2s_key` | 32+ | service-to-service calls | backend, claw and claw-auth Secrets |
| `claw_s2s_key` | 32+ | claw to claw-auth | claw and claw-auth Secrets |
| `claw_auth_encryption_key` | exactly 64 hex | credentials claw-auth stores | `xyne-claw-auth-secrets` |
| `ysweet_auth`, `ysweet_server_token` | from the same `gen-auth` run | the y-sweet signing key and the token the backend presents | `xyne-ysweet-secrets`, `xyne-backend-secrets` |
| `transcription_agent_api_key` | 32+ | backend to transcription agent | `xyne-transcription-agent-secrets` |
| `google_client_id`, `google_client_secret` | **required**; the backend does not start without them | Google sign-in for the backend and claw-auth | backend and claw-auth Secrets |
| `litellm_api_key` | optional | claw's model access | `xyne-claw-secrets` |
| `hindsight_api_key` | optional | claw's key to the Hindsight API | `xyne-claw-secrets` |
| `hindsight_llm_api_key` | required with `enable_hindsight` | Hindsight's own LLM key | `hindsight-secrets` in the `hindsight` namespace |

## Google sign-in

Every install needs a Google OAuth client; it can live in any Google Cloud project.

1. <https://console.cloud.google.com/apis/credentials/consent>: configure the consent screen,
   *Internal* when every user is in your Google Workspace, otherwise *External* with your domain
   authorised.
2. <https://console.cloud.google.com/apis/credentials>: *Create credentials → OAuth client ID →
   Web application*:

   | Field | Value |
   |---|---|
   | Authorized JavaScript origins | `https://<domain>` |
   | Authorized redirect URIs | `https://<domain>/api/auth/exchange` |

3. Give the client ID (it ends in `.apps.googleusercontent.com`) and secret to `secrets.sh`, or
   put them in `app_secrets`.

`curl -sS https://<domain>/api/v2/auth/providers` shows `"google":true` once the backend has it.

## Adding keys the tree does not know about

`extra_secret_data` merges keys into any of the nine Secrets the install writes:

```hcl
extra_secret_data = {
  xyne-transcription-agent-secrets = {
    AZURE_OPENAI_STT_API_KEY = "…"
  }
}
```

A key reaches a pod only if its chart maps it: add a `secretEnv` entry through
`apps.<chart>.values`, or `envFromSecrets` for the whole Secret. The whole Secret also brings the
empty `AWS_ACCESS_KEY_ID` of `managed` storage mode, which the AWS SDK treats as set, so prefer
single keys. Secrets outside these (registry
pull secrets, `xyne-pg-backup`, `xyne-lighton-model-secrets`) are created by you or an overlay.

## Rotation

Change the value in the secrets file and re-apply the stage that owns it. `02-platform` passes a
checksum of every Secret it writes to the root chart, which stamps a `checksum/secrets` annotation
on each app from the Secrets that app reads. A changed Secret changes the annotation, so Argo CD
restarts exactly the apps that read it.

| Value | Re-apply | Also |
|---|---|---|
| any `app_secrets` field, `extra_secret_data` | `--only platform` | nothing |
| `postgres_password`, managed | both stages (`01-infra` changes the role, `02-platform` the URLs) | nothing |
| `postgres_password`, in-cluster | `--only platform`; CloudNativePG applies it to the role | nothing |
| `redis_auth`, AWS managed | both stages; ElastiCache accepts the old and new token until the next change | roll the LiveKit VMs |
| `redis_auth`, in-cluster | both stages | `kubectl -n xyne-apps rollout restart statefulset/xyne-redis` |
| `storage_credentials` | both stages | restart MinIO in `incluster` mode |
| `livekit_api_key`, `livekit_api_secret` | both stages | on GCP and Azure restart the LiveKit groups ([calls](../features/calls.md#changing-the-configuration-or-the-keys)); AWS replaces them itself |
| `hindsight_llm_api_key` | `--only platform` | `kubectl -n hindsight rollout restart deploy/hindsight-api` |

Some rotations have consequences beyond a restart: a new `zero_auth_secret` or `jwt_secret` signs
every user out, and `encryption_key` and `claw_auth_encryption_key` cannot be rotated at all
without re-encrypting stored data, for which the application has no tooling.

## What never to commit

- `deployment/environments/<env>/` for any `<env>` that is not `example-*`; git ignores them.
  Keep real environments in a private repository and use `--env-dir`.
- The generated `backend.tf` files and any `.terraform/`, `*.tfstate*`, `*.tfplan`; ignored too.
- The state itself: restrict the state bucket to the deployers and keep versioning on.
